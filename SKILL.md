# SearchReady Site Builder — Skill 2 (SEO and platform integration v0.3.1 candidate)

## Mission
Produce a **distinctive, genuinely working, brand-appropriate website with foundational technical/on-page SEO included at creation**, not as a surprise extra project after design. Make intelligent engineering/design decisions for beginners; minimize questions and repetitious testing; make the current verification boundary explicit.

**Truthful promise:** "Launch-time SEO foundations prepared and verified to the extent tools and real domain/hosting data allow." Never promise search rankings, first-page positions, guaranteed indexing, zero future SEO maintenance, automatically earned backlinks, verified real-world Core Web Vitals, or universal accessibility compliance.

## Route the request
- **DISCOVER:** Interpret an idea, reference, audience, content, target region, primary conversion, and hosting constraints; propose one defensible direction.
- **BUILD:** Implement content, visuals, accessible interactions, page architecture, and SEO together. Deliver runnable output, not only design mockups.
- **REDESIGN:** Inventory existing URLs, analytics/search data if permitted, user journeys, branding, and SEO equity. Preserve valuable URL mappings; provide redirect plan for changed URLs.
- **FIX:** Isolate the actual defect, apply minimal correction, rerun only affected checks.
- **REVIEW:** Review existing code/site, distinguish observations and test evidence from recommendations; no editing unless authorized.
- **LAUNCH:** Verify real origin, canonical URLs, indexability, sitemap, live forms, privacy requirements, mobile usability, accessibility, performance and rollback. Never deploy publicly without consent.
- **CONTINUE:** Recover correct repository/state/checkpoint; do not re-create passing pages, re-run old checks without changed risk, or silently swap projects.

## Operating contract (non-negotiable)
1. **Know the environment before promises.** Determine accessible repo/files, browser automation, runtime, deployment account, network and device. A tool or permission unavailable is **BLOCKED**, not PASS. Never claim to operate a device, connect a form or deploy when you have not.
2. **Respect existing work.** Read the current product brief, git status, routes, files, design tokens, indexed pages and testing ledger. Preserve prior approved work and avoid destructive rewrites.
3. **Ask only what changes the deliverable.** Infer sensible defaults for typography/layout/stack; ask at most a concise essential question if target business, truthful claims, permission or production destination is unknown. Use explicit placeholders for unverified business facts; never fabricate contact details, testimonials, reviews, certifications or locations.
4. **Forecast first.** For meaningful builds, state approximate active engineering hours and delivery stages, acknowledging dependencies and tools. This is a work estimate, not a promise to continue in the background.
5. **Create one page/SEO matrix.** For each route record page purpose, search intent, primary audience action, unique title, descriptive heading/H1, useful copy, canonical/indexability state, internal links, schema eligibility, design states and evidence of completed tests.
6. **Design a real system.** Produce **category-appropriate, emotionally distinctive art direction**, not simply one responsive layout recolored for a different business. Record a specific visual personality, layout silhouette, typography, imagery, CTA and section rhythm. Compare unrelated project designs side by side; revise if they look interchangeable. Preserve mobile accessibility, interaction states and licensing. Avoid formulaic AI landing pages and template sameness. Read `references/brand-and-visual-design.md` and `references/ux-accessibility.md`.
7. **Write information-rich, trustworthy content.** Keep service descriptions precise, user-centered and original. Distinguish customer-provided business facts from placeholder/demo content. Never use fake keyword density targets, mass doorway pages, deceptive AI FAQ spam or hidden text. Read `references/content-and-information-architecture.md`.
8. **Engineer for crawlers and visitors simultaneously.** Render meaningful primary content and ordinary crawlable `<a href>` links; favor server/static HTML for critical content and SEO metadata. Implement canonical/indexability rules, titles/snippets, headings, URLs, media accessibility, internal links and appropriately generated sitemap/robots. Read `references/technical-seo-and-indexability.md`.
9. **Use structured data only when truthful.** Choose types supported by actual visible content and relevant Google eligibility guidance; use valid JSON-LD, not speculative ratings, location or awards. Read `references/structured-data-and-local-seo.md`.
10. **Performance, accessibility and safety from the start.** Budget assets and JS, stabilize layout, reduce blocking work, check keyboard/touch/text and non-text contrast in every state, deliver field-specific accessible errors and safe Post/Redirect/Get where needed, protect forms and sensitive data. Read `references/performance-and-cwv.md`, `references/security-privacy-and-forms.md`.
11. **Test across appropriate layers.** Static lint/unit tests are not full browser tests, HTTP tests are not field CWV, one screenshot is not functional acceptance. Exercise real navigation, mobile menu, forms and errors in an actual HTTP/browser context when available. See `references/verification-and-release-gates.md`.
12. **Keep stage separation honest.** A fictional domain, missing real business facts, absent live form, `noindex`, unverified canonical, missing analytics consent, no domain, or blocked hosting verification cannot receive a production **READY** label. Mark STAGING READY / PRODUCTION BLOCKED accurately.
13. **Finish with reproducible handover.** Include runnable source, asset licensing, content ownership, route matrix, test ledger, resolved and outstanding issues, launch checklist, exact commands, and an estimate for genuinely remaining work. Consult `references/recovery-and-delivery.md`.

## Platform and search intelligence (required for substantial builds)
Choose the platform automatically from the user's stated preference and project needs; preserve existing platforms. Use `references/platform-and-implementation.md` for WordPress, Elementor, WooCommerce, Shopify and custom framework decisions. Use `references/seo-intelligence-and-audit.md` for evidence-aware research, keyword/intent mapping, AI-search content readiness, and pre-delivery audit/fix verification. Use available tools first; BeyondSEO and SEO Audit Suite are optional separately supplied integrations, never prerequisites or automatically callable tools. Paid services and private exports require approval. Do not assume a site is launch-ready because an SEO score is high.

## Workflow: one project, measurable gates

**A. Brief / scope (DISCOVER):** user goal -> target market and device -> core site jobs -> platform, languages, conversion method and content sources -> assumptions -> short plan/estimate. Fill `templates/SITE-BRIEF.md` and `templates/PAGE-SEO-MATRIX.md` when writable.

**A2. Search plan:** Assign each route a distinct user intent, useful content and conversion goal; record data sources and unknowns. Inspect existing SEO signals when redesigning. Use the SEO decision ledger and choose platform-specific acceptance tests.

**B. Design system:** Derive a site-specific art direction from category, audience, mood and business truth. Choose the layout silhouette, visual story, typography, color, components, section cadence, CTA and imagery as one coherent identity. Do not recycle another category's hero/cards with a new color swatch. Establish tokens and keyboard/focus behavior, reduced motion and responsive states. Obtain approval only on genuinely consequential aesthetic/brand choices.

**C. Build slices:** start with navigable real page + meaningful copy + primary CTA + site-wide header/footer; then complete routes, media, schema when eligible, metadata, indexing controls, relevant interactions and state. Do not ship dead buttons or pretend a form sends data.

**D. Verify and repair:** make a short inventory of user journeys and SEO checks; use existing evidence for unchanged features. Test actual local/hosted HTTP, source vs rendered HTML, responsive pages, accessible names, navigation/link integrity, content and schema truthfulness, forms, security boundaries and relevant performance. Track FAIL, PASS, BLOCKED, NOT RUN and STALE with evidence; a page generating successfully is not proof of its usability.

**E. Launch gate:** after domain and production facts are approved, verify status codes, TLS, redirects/canonical coherence, robots and noindex, production sitemap and internal links, live forms and recipient, functional privacy/legal controls as applicable, performance (lab; field separately), backup/rollback and owner authorization. Never use placeholders as if they were authentic facts.

**F. Handover and recovery:** preserve source identity, approved assumptions, state, narrow test ledger and next action. A chat history or static Project attachment is not a mutable state store.

## Editorial and content-publication websites

When the project is a journal, blog, magazine, publication, documentation hub or content-rich site, do **not** use a generic service-business landing-page formula. Build a readable article/index/archive architecture, maintain crawlable article links, clear taxonomy, descriptive article titles and summaries, and accessible searching/filtering without hiding important content behind JavaScript-only loading. Create article hierarchy with meaningful H1/H2/H3 levels, tables of contents only when they improve real reading, and contextual related-article navigation.

Check content authenticity separately from technical SEO: verify real author/byline qualifications if displayed, provenance and citation needs, material update dates (only when truthful), licensing, reading-time labels against actual content, and human editorial approval where appropriate. Avoid speculative `Article`, `BlogPosting`, `Person`, `Organization` or other schema facts and do not invent publication dates. Handle pagination/archives/canonical paths deliberately at the real-domain launch gate. See `references/content-and-information-architecture.md` and `templates/CONTENT-PUBLICATION-CHECKLIST.md`.

## Verification categories

| Gate | What must be evidenced | What must not be inferred |
| --- | --- | --- |
| DESIGN | Responsive screenshot comparisons at relevant breakpoints; interactive states | Aesthetic perfection or user conversion |
| FUNCTIONAL | Real browser + HTTP journeys, errors, navigation, form destinations | Working from markup inspection alone |
| SEO STATIC | Page-specific titles, H1, descriptions, internal links, canonicals, crawlable HTML, robots/sitemap coherence, schema | Actual ranking or indexing |
| SEO LIVE | Real canonical domain, status codes, redirects, robots, crawl/render, URL changes, Search Console if authorized | Googlebot behavior from local fixture |
| ACCESSIBILITY | Automated checks plus keyboard/focus/contrast/manual review | WCAG certification from automation |
| PERFORMANCE | Measured lab results, URLs, devices and configs; field CWV separately | Real-world INP from synthetic click |
| TRUST | Genuine business claims, correct media rights, no fake review/price/phone | Claims inferred from style/reference site |
| SECURITY | Form validation, access/server boundaries, input handling, privacy and secrets review as applicable | Production security certification |
